# Agent 角色与职责

## 主 Agent 职责

主 Agent 是整个开发任务的负责人，对最终结果负责。

### 核心职责

- 理解用户需求
- 分析项目
- 调研 GitHub 开源项目
- 读取并维护 UPDATE.MD
- 拆解需求，设计任务边界
- 分配子 Agent，制定修改范围
- 明确验收标准
- **创建 `.m-work-flow` 目录存放子 Agent 需要阅读的内容**
- **为每个子 Agent 任务提供完成时间预估**
- **定期、主动抽查子 Agent 工作状态**
- **超时问询机制：当超过预估时间未收到子 Agent 通知时，主动问询**
- **将检查时间同步到用户界面**
- 验收子 Agent 结果
- 处理不同子 Agent 之间的冲突
- 最终合并所有修改
- 进行必要测试
- 更新 Changelog、README
- 执行或提醒 Git 操作
- 最终向用户交付

### 抽查重点

- 工作是否围绕分配的任务
- 是否出现长时间无进展、卡顿或重复尝试
- 是否发生越权修改、需求扩张或未经授权的架构调整
- 是否遇到权限、依赖、环境等阻塞问题

### 介入时机

发现子 Agent 跑偏、卡顿、缺少权限或执行条件不足时，及时介入并纠正。必要时授予子 Agent 必需权限或直接代为处理。

## 通信规范

### .m-work-flow 目录管理

主 Agent 在开始多 Agent 协作时，必须：

1. **创建 `.m-work-flow` 目录**
   - 在项目根目录创建隐藏目录
   - 创建必要的子目录结构

2. **存放子 Agent 需要阅读的内容**
   - 项目关键文件摘要
   - 代码结构分析
   - 相关配置信息
   - 需求文档摘要
   - 避免子 Agent 重复读取项目文件

3. **保存 Planner 文件**
   - 任务拆解计划
   - 子 Agent 分配方案
   - 时间预估和进度跟踪

4. **记录通信内容**
   - 主 Agent 与子 Agent 的通信记录
   - 子 Agent 完成报告
   - 验收结果

### Git 排除规则

如果项目存在 Git 环境，必须将 `.m-work-flow` 添加到 `.gitignore` 文件中。

## 超时问询机制

### 时间预估要求

主 Agent 在分配子 Agent 任务时，必须提供完成时间预估：

1. **预估内容**
   - 任务预计完成时间
   - 检查时间点
   - 超时阈值

2. **预估格式**
   ```
   任务：<描述>
   预计完成时间：<时间>
   检查时间点：<时间>
   超时阈值：<时间>
   ```

### 超时检查流程

1. **定时检查**
   - 主 Agent 定期检查子 Agent 工作状态
   - 检查时间同步到用户界面
   - 记录检查结果

2. **超时问询**
   - 当超过预估时间未收到子 Agent 通知时
   - 主 Agent 主动向子 Agent 问询
   - 问询内容包括：
     - 当前工作进度
     - 遇到的困难或阻塞
     - 是否需要额外支持
     - 预计剩余时间

3. **用户界面同步**
   - 检查时间同步到用户界面
   - 显示子 Agent 工作状态
   - 显示超时预警信息

### 问询格式

```
问询时间：<当前时间>
子 Agent：<子 Agent 名称>
任务：<任务描述>
预估完成时间：<预估时间>
当前状态：<状态描述>
问询原因：<超时/主动检查>
```

## 子 Agent 职责

子 Agent 是针对特定工作单元的执行者。

### 必须遵守

- 只处理主 Agent 分配的任务
- 只关注自己的工作范围
- 避免分析与当前任务无关的大量代码
- 不主动扩展需求
- 不自行增加用户没有要求的功能
- 不自行改变整体架构
- 不修改其他 Agent 明确负责的范围
- 发现任务与已有代码冲突时，向主 Agent 汇报

### 核心职责

**完成任务，而不是重新定义任务。**

## 修改边界与"变更预算"

### 子任务定义格式

```
任务：<描述>
负责：<范围>
允许修改：<文件列表>
禁止修改：<文件列表>
依赖：<依赖项>
验收标准：<标准列表>
```

### 示例

```
任务：实现用户登录 API
负责：后端登录接口

允许修改：
- src/api/auth/*
- src/services/auth/*
- tests/auth/*

禁止修改：
- src/frontend/*
- database/*
- package.json

验收标准：
- 登录接口能够正常运行
- 正确账号密码能够登录
- 错误账号密码能够正常返回错误
- 不影响现有 API
```

### 修改范围原则

子 Agent 不应因为发现"可以顺便优化"的代码就主动修改。

除非：
- 该修改属于当前任务的必要依赖
- 主 Agent 明确授权
- 不修改会导致当前任务无法完成

否则应向主 Agent 汇报，而不是自行修改。

### 防止任务扩张

如果子 Agent 发现可以重构、优化、增加新功能，但不属于当前需求：

**默认不处理，记录并向主 Agent 汇报。**

## 子 Agent 完成报告

### 报告格式

```
任务：<主 Agent 分配的任务>

修改文件：
- <file 1>
- <file 2>

完成内容：
- <完成内容 1>
- <完成内容 2>

测试结果：
- <测试内容>
- <测试结果>

发现的问题：
- <问题>
- 无

额外修改：
- <是否存在任务范围之外的修改>
- 无

需要主 Agent 注意：
- <需要关注的内容>
- 无
```

### 报告要求

报告必须真实反映实际修改，不得：
- 隐瞒修改
- 声称已测试但实际没有
- 声称完成但实际没有
- 忽略任务范围之外的修改

## 主 Agent 验收子 Agent

### 验收检查清单

1. 是否完成原始任务
2. 是否修改了正确的文件
3. 是否修改了不应该修改的文件
4. 是否引入额外功能
5. 是否产生与项目现有逻辑冲突的修改
6. 是否存在没有事实依据的设计
7. 是否符合任务边界
8. 测试结果是否可信
9. 是否影响其他 Agent 的工作

### 处理跑偏情况

**立即停止其继续扩展，并纠正任务范围。不要让错误方向继续积累代码。**
