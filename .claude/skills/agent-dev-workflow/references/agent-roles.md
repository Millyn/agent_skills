# Agent 角色与职责

> 本文是以下内容的唯一权威来源：四类角色职责、GUI 展示标识、任务边界格式、完成与测试报告格式、验收流程。
> Thread 与 Agent 的概念区别和 `create_thread` 使用规则见 [thread-management.md](thread-management.md)；AGENTS.md 中保存了任务边界格式的速查副本。

## 层级与角色总览

| 层级 | 角色 | 核心职责 |
|------|------|----------|
| 主 Thread | 流程统筹 Agent | 需求拆解、`create_thread` 创建子 Thread、最终验收和交付 |
| 子 Thread | 子 Thread 主 Agent | 任务规划、拆解、下发给子 Agent |
| 子 Thread 内 | 任务执行 Agent（子 Agent） | 执行具体技术任务 |
| 子 Thread 内 | 质量验证 Agent（测试 Agent） | 唯一的正式定向测试层 |

## GUI 展示标识规范

- 四类角色的展示名称固定为："流程统筹 Agent""子 Thread 主 Agent""任务执行 Agent""质量验证 Agent"，不得仅显示"主 Agent""子 Agent""测试 Agent"
- 展示名称必须与当前任务状态同时显示：`<角色展示名称>｜<任务状态>`，例如：`任务执行 Agent｜工作中`
- 子 Thread 级别需带 Thread 标识：`Thread:<Thread名称>｜<角色展示名称>｜<任务状态>`，例如：`Thread:thread-翻译功能｜任务执行 Agent｜工作中`
- Thread 名称使用注册表中的稳定名称（见 [thread-management.md](thread-management.md)）

## 流程统筹 Agent（主 Thread）

整个开发任务的负责人，对最终结果负责。

### 核心职责

- 理解用户需求、分析项目、调研 GitHub 开源项目（流程见 [development-workflow.md](development-workflow.md)）
- 按 UPDATE.MD 确定版本目标（见 [version-management.md](version-management.md)）
- 拆解需求，按 `create_thread` 规则创建子 Thread（见 [thread-management.md](thread-management.md)），同领域优先复用已有专项 Thread
- 为每个子 Thread 定义任务边界（使用下文「主 Thread 任务拆解格式」）
- 创建 `.m-work-flow` 目录并向子 Thread 提供上下文（目录规范见 [development-workflow.md](development-workflow.md)）
- 为每个子 Thread 提供完成时间预估，定期抽查子 Thread 状态并执行超时问询（机制见 [development-workflow.md](development-workflow.md)）
- 发现子 Thread 跑偏、卡顿、缺少权限或执行条件不足时及时介入纠正；必要时授予权限或代为处理
- 验收子 Thread 结果（见下文「验收流程」），处理跨子 Thread 冲突，最终合并所有修改
- 只测跨子 Thread 交集和整体启动冒烟，复用子 Thread 测试结论（见 [testing.md](testing.md)）
- 更新 Changelog、README，执行或提醒 Git 操作，最终向用户交付（见 [delivery.md](delivery.md)）

### 抽查重点

- 子 Thread 工作是否围绕分配的任务
- 是否长时间无进展、卡顿或重复尝试
- 是否发生越权修改、需求扩张或未经授权的架构调整
- 是否遇到权限、依赖、环境等阻塞问题

## 子 Thread 主 Agent

子 Thread 内部的规划者，负责将子 Thread 任务进一步拆解并下发给子 Agent，对主 Thread 汇报。

### 核心职责

- 接收主 Thread 分配的任务，分析任务细节和依赖关系
- 将任务拆解为最小可执行单元，为每个子 Agent 定义任务边界（使用下文「子 Thread 任务定义格式」）
- 为子 Agent 提供时间预估和检查点，监督进度并执行超时问询（机制见 [development-workflow.md](development-workflow.md)）
- 验收子 Agent 完成结果（见下文「验收流程」），向主 Thread 汇报整体完成情况
- 修改范围很小且风险低时，可不单独分配质量验证 Agent，以任务执行 Agent 自测加主 Agent 定向抽查代替，并在子 Thread 完成报告中记录决定和理由（见 [testing.md](testing.md) 小型任务简化）

## 任务执行 Agent（子 Agent）

针对特定工作单元的执行者。**完成任务，而不是重新定义任务。**

### 必须遵守

- 只处理子 Thread 主 Agent 分配的任务，避免分析与当前任务无关的大量代码
- 不主动扩展需求，不自行增加用户没有要求的功能，不自行改变整体架构
- 不修改其他 Agent 明确负责的范围
- 发现任务与已有代码冲突时，向子 Thread 主 Agent 汇报

### 修改边界与"变更预算"

不因"可以顺便优化"而主动修改代码，除非满足以下条件之一：

- 该修改属于当前任务的必要依赖
- 子 Thread 主 Agent 明确授权
- 不修改会导致当前任务无法完成

否则应向子 Thread 主 Agent 汇报，而不是自行修改。发现可以重构、优化、增加新功能但不属于当前需求时：**默认不处理，记录并向子 Thread 主 Agent 汇报。**

### 自测要求

完成后只做最小自测（编译、启动、所改功能点本身能跑通），完整定向验证由质量验证 Agent 负责，不在子 Agent 层重复。

## 质量验证 Agent（测试 Agent）

唯一的正式定向测试层。测试范围由子 Thread 主 Agent 在任务边界中确定（修改范围、影响范围、测试目标、测试边界）；除非用户明确要求，不默认执行全量测试，也不重复任务执行 Agent 已完成的自测项。测试策略、范围决策和全量回归触发条件见 [testing.md](testing.md)。其测试报告是子 Thread 验收、主 Thread 验收和最终交付汇总的唯一测试证据来源。

## 任务边界格式（权威模板）

### 主 Thread 任务拆解格式

主 Thread 创建子 Thread 时必须定义：

```
子 Thread：<名称>
任务：<描述>
负责：<范围>
依赖：<其他子 Thread>
修改范围：<实际允许变更的模块、文件或功能>
影响范围：<直接调用链、依赖模块、资源、数据或用户流程>
测试目标：<需要验证的行为和风险>
测试边界：<本次默认不覆盖的范围；如需全量回归需明确说明>
验收标准：<标准列表>
```

### 子 Thread 任务定义格式

子 Thread 主 Agent 分配子 Agent 任务时必须定义：

```
任务：<描述>
负责：<范围>
允许修改：<文件列表>
禁止修改：<文件列表>
依赖：<依赖项>
修改范围：<实际允许变更的模块、文件或功能>
影响范围：<直接调用链、依赖模块、资源、数据或用户流程>
测试目标：<需要验证的行为和风险>
测试边界：<本次默认不覆盖的范围；如需全量回归需明确说明>
验收标准：<标准列表>
```

子 Thread 主 Agent 分配任务时必须填写四项测试相关信息；质量验证 Agent 依据这些信息制定测试（详见 [testing.md](testing.md) 测试范围决策）。

### 示例

```
任务：实现用户登录 API
负责：后端登录接口

允许修改：
- src/api/auth/*
- src/services/auth/*
- tests/auth/*

禁止修改：
- src/frontend/*
- database/*
- package.json

验收标准：
- 登录接口能够正常运行
- 正确账号密码能够登录
- 错误账号密码能够正常返回错误
- 不影响现有 API
```

## 完成与测试报告格式（权威模板）

报告必须真实反映实际修改，不得隐瞒修改、声称已测试但实际没有、声称完成但实际没有、忽略任务范围之外的修改。

### 任务执行 Agent 完成报告

```
任务：<子 Thread 主 Agent 分配的任务>

修改文件：
- <file 1>

完成内容：
- <完成内容 1>

测试结果：
- <最小自测方式与结果：编译/启动/所改功能点跑通；不要求覆盖影响链路>

发现的问题：
- <问题或"无">

额外修改：
- <是否存在任务范围之外的修改，无则填"无">

需要子 Thread 主 Agent 注意：
- <需要关注的内容，无则填"无">
```

### 质量验证 Agent 测试报告

```
测试对象：<修改范围和影响范围>

测试结果：
- <通过/失败及详情>

实际测试范围：
- <已执行的修改范围、直接影响链路和必要的最小冒烟验证>

未测试范围及原因：
- <按测试边界列出；无则填写"无">

范围扩大及理由：
- <超出分配测试边界时必填；无则填写"无">

发现的问题：
- <问题或"无">
```

### 子 Thread 完成报告

```
子 Thread：<名称>

完成任务：
- <任务 1>

包含子 Agent：
- <子 Agent 1>

测试情况：
- <质量验证 Agent 测试结论及来源；未单独分配质量验证 Agent 时记录简化决定和理由>

汇总结果：
- <整体完成情况>

需要主 Thread 注意：
- <需要关注的内容，无则填"无">
```

## 验收流程

### 子 Thread 主 Agent 验收子 Agent

检查清单：

1. 是否完成原始任务
2. 是否修改了正确的文件
3. 是否修改了不应该修改的文件
4. 是否引入额外功能
5. 是否产生与项目现有逻辑冲突的修改
6. 是否存在没有事实依据的设计
7. 是否符合任务边界
8. 测试结果是否可信
9. 是否影响其他子 Agent 的工作

验收方式为审查证据：核对报告、修改文件和测试结论，不重新执行已被覆盖的测试；仅在发现覆盖缺口时补测缺口。

发现跑偏时：**立即停止其继续扩展，并纠正任务范围。不要让错误方向继续积累代码。**

### 主 Thread 验收子 Thread

检查清单：

1. 子 Thread 是否完成分配的所有任务
2. 子 Thread 内部是否有未解决的冲突
3. 子 Thread 的修改是否影响其他子 Thread
4. 整体结果是否符合用户需求
5. 是否存在超出需求范围的功能
6. 测试结果是否可信

验收方式为审查证据：汇总各级测试报告，只补测跨子 Thread 交集缺口和整体启动冒烟，不重复任何子 Thread 已覆盖的测试范围。
