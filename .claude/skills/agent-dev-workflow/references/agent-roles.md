# Agent 角色与职责

## 多层级架构概述

本规范采用 **主 Session → 子 Session → 子 Agent** 的多层级架构：

```
主 Session（流程统筹 Agent）
    │
    ├── 拆解需求
    ├── 创建子 Session
    │
    └── 子 Session A
        │
        ├── 子 Session 主 Agent（规划下发）
        │
        ├── 子 Agent 1（执行任务）
        ├── 子 Agent 2（执行任务）
        └── 子 Agent N...
```

### 层级职责

| 层级 | 角色 | 核心职责 |
|------|------|----------|
| 主 Session | 流程统筹 Agent | 需求拆解、创建子 Session、最终验收和交付 |
| 子 Session | 子 Session 主 Agent | 任务规划、拆解、下发给子 Agent |
| 子 Agent | 任务执行 Agent | 执行具体技术任务 |

### Session 与 Agent 的区别

- **Session**：任务执行容器，负责落地主 Session 拆解下来的可执行任务
- **Agent**：任务执行者，有多种角色区分（统筹、执行、测试）

子 Session 不会像 Agent 有多个角色，只负责执行主 Session 拆解下来的可执行任务，内部由子 Session 主 Agent 规划具体执行细节。

---

## 主 Session 层级

### 流程统筹 Agent（主 Session Agent）职责

流程统筹 Agent 是整个开发任务的负责人，对最终结果负责。

#### 核心职责

- 理解用户需求
- 分析项目
- 调研 GitHub 开源项目
- 读取并维护 UPDATE.MD
- **拆解需求，创建子 Session**
- **在 GUI 多会话环境中将子 Session 创建为真实可视化会话，并维护 Session 注册表**
- **同领域任务优先复用已有专项 Session，而非新建**
- **为每个子 Session 划分任务边界**
- 明确验收标准
- **创建 `.m-work-flow` 目录存放子 Session 和子 Agent 需要阅读的内容**
- **为每个子 Session 提供完成时间预估**
- **定期、主动抽查子 Session 工作状态**
- **超时问询机制：当超过预估时间未收到子 Session 通知时，主动问询**
- **将检查时间同步到用户界面**
- 验收子 Session 结果
- 处理不同子 Session 之间的冲突
- 最终合并所有修改
- 只测跨子 Session 交集和整体启动冒烟，复用子 Session 测试结论
- 更新 Changelog、README
- 执行或提醒 Git 操作
- 最终向用户交付

#### 抽查重点

- 子 Session 工作是否围绕分配的任务
- 是否出现长时间无进展、卡顿或重复尝试
- 是否发生越权修改、需求扩张或未经授权的架构调整
- 是否遇到权限、依赖、环境等阻塞问题

#### 介入时机

发现子 Session 跑偏、卡顿、缺少权限或执行条件不足时，及时介入并纠正。必要时授予子 Session 必需权限或直接代为处理。

#### GUI 展示标识

- GUI 展示名称固定为"流程统筹 Agent"，不得仅使用"主 Agent"作为展示名称。
- 展示名称必须与当前任务状态同时显示，格式为：`流程统筹 Agent｜<任务状态>`。

---

## 子 Session 层级

### 子 Session 主 Agent 职责

子 Session 主 Agent 是子 Session 内部的规划者，负责将子 Session 任务进一步拆解并下发给子 Agent。

#### 核心职责

- 接收主 Session 分配的任务
- 分析任务细节和依赖关系
- 将任务拆解为可执行的子任务
- 分配给具体的子 Agent
- 监督子 Agent 执行进度
- 验收子 Agent 完成结果
- 向主 Session 汇报整体完成情况

#### 任务规划要求

- 将子 Session 任务拆解为最小可执行单元
- 为每个子 Agent 定义明确的任务边界
- 协调子 Agent 之间的依赖关系
- 提供时间预估和检查点

#### GUI 展示标识

- GUI 展示名称固定为"子 Session 主 Agent"，不得仅使用"主 Agent"作为展示名称。
- 展示名称必须与当前任务状态同时显示，格式为：`Session:<Session名称>｜子 Session 主 Agent｜<任务状态>`。

#### 超时问询机制

- 子 Session 主 Agent 定期检查子 Agent 工作状态
- 超时时主动向子 Agent 问询
- 问询内容：当前工作进度、遇到的困难、是否需要支持、预计剩余时间

#### 问询格式

```
问询时间：<当前时间>
层级：子 Session
角色：子 Session 主 Agent
任务：<任务描述>
预估完成时间：<预估时间>
当前状态：<状态描述>
问询原因：<超时/主动检查>
```

## 子 Agent 层级

### 任务执行 Agent（子 Agent）职责

任务执行 Agent 是针对特定工作单元的执行者。

GUI 展示名称固定为"任务执行 Agent"，并必须与当前任务状态同时显示，格式为：`Session:<Session名称>｜任务执行 Agent｜<任务状态>`。任务分配、进度抽查和超时问询中均应使用该稳定职能名称，避免与其他角色混淆。

#### 必须遵守

- 只处理子 Session 主 Agent 分配的任务
- 只关注自己的工作范围
- 避免分析与当前任务无关的大量代码
- 不主动扩展需求
- 不自行增加用户没有要求的功能
- 不自行改变整体架构
- 不修改其他 Agent 明确负责的范围
- 发现任务与已有代码冲突时，向子 Session 主 Agent 汇报

#### 核心职责

**完成任务，而不是重新定义任务。**

完成后只做最小自测（编译、启动、所改功能点本身能跑通），完整定向验证由质量验证 Agent 负责，不在子 Agent 层重复。

## 修改边界与"变更预算"

### 主 Session 任务拆解格式

主 Session 在创建子 Session 时必须定义：
```
子 Session：<名称>
任务：<描述>
负责：<范围>
依赖：<其他子 Session>
验收标准：<标准列表>
```

### 子 Session 任务定义格式

子 Session 主 Agent 在分配子 Agent 任务时必须定义：
```
任务：<描述>
负责：<范围>
允许修改：<文件列表>
禁止修改：<文件列表>
依赖：<依赖项>
验收标准：<标准列表>
```

### 示例

```
任务：实现用户登录 API
负责：后端登录接口

允许修改：
- src/api/auth/*
- src/services/auth/*
- tests/auth/*

禁止修改：
- src/frontend/*
- database/*
- package.json

验收标准：
- 登录接口能够正常运行
- 正确账号密码能够登录
- 错误账号密码能够正常返回错误
- 不影响现有 API
```

### 修改范围原则

子 Agent 不应因为发现"可以顺便优化"的代码就主动修改。

除非：
- 该修改属于当前任务的必要依赖
- 子 Session 主 Agent 明确授权
- 不修改会导致当前任务无法完成

否则应向子 Session 主 Agent 汇报，而不是自行修改。

### 防止任务扩张

如果子 Agent 发现可以重构、优化、增加新功能，但不属于当前需求：

**默认不处理，记录并向子 Session 主 Agent 汇报。**

## 子 Agent 完成报告

### 报告格式

```
任务：<子 Session 主 Agent 分配的任务>

修改文件：
- <file 1>
- <file 2>

完成内容：
- <完成内容 1>
- <完成内容 2>

测试结果：
- <最小自测方式与结果：编译/启动/所改功能点跑通；不要求覆盖影响链路>

发现的问题：
- <问题>
- 无

额外修改：
- <是否存在任务范围之外的修改>
- 无

需要子 Session 主 Agent 注意：
- <需要关注的内容>
- 无
```

### 报告要求

报告必须真实反映实际修改，不得：
- 隐瞒修改
- 声称已测试但实际没有
- 声称完成但实际没有
- 忽略任务范围之外的修改

## 子 Session 完成报告

### 报告格式

```
子 Session：<名称>

完成任务：
- <任务 1>
- <任务 2>

包含子 Agent：
- <子 Agent 1>
- <子 Agent 2>

测试情况：
- <质量验证 Agent 测试结论及来源；未单独分配质量验证 Agent 时记录简化决定和理由>

汇总结果：
- <整体完成情况>

需要主 Session 注意：
- <需要关注的内容>
- 无
```

## 质量验证 Agent（测试 Agent）职责

质量验证 Agent 是唯一的正式定向测试层，负责验证本次修改范围内的功能，GUI 展示名称固定为"质量验证 Agent"，并必须与当前任务状态同时显示，格式为：`Session:<Session名称>｜质量验证 Agent｜<任务状态>`。测试范围由子 Session 主 Agent 根据修改范围和影响范围确定；除非明确要求，不默认执行全量测试，也不重复执行任务执行 Agent 已完成的自测项。其测试报告是子 Session 验收、主 Session 验收和最终交付汇总的测试证据来源。

### 测试报告格式

```
测试对象：<修改范围和影响范围>

测试结果：
- <通过/失败及详情>

实际测试范围：
- <已执行的修改范围、直接影响链路和必要的最小冒烟验证>

未测试范围及原因：
- <按测试边界列出；无则填写"无">

范围扩大及理由：
- <超出分配测试边界时必填；无则填写"无">

发现的问题：
- <问题>
- 无
```

## 验收流程

### 子 Session 主 Agent 验收子 Agent

#### 验收检查清单

1. 是否完成原始任务
2. 是否修改了正确的文件
3. 是否修改了不应该修改的文件
4. 是否引入额外功能
5. 是否产生与项目现有逻辑冲突的修改
6. 是否存在没有事实依据的设计
7. 是否符合任务边界
8. 测试结果是否可信
9. 是否影响其他子 Agent 的工作

验收方式为审查证据：核对报告、修改文件和测试结论，不重新执行已被覆盖的测试；仅在发现覆盖缺口时补测缺口。

#### 处理跑偏情况

**立即停止其继续扩展，并纠正任务范围。不要让错误方向继续积累代码。**

### 主 Session 验收子 Session

#### 验收检查清单

1. 子 Session 是否完成分配的所有任务
2. 子 Session 内部是否有未解决的冲突
3. 子 Session 的修改是否影响其他子 Session
4. 整体结果是否符合用户需求
5. 是否存在超出需求范围的功能
6. 测试结果是否可信

验收方式为审查证据：汇总各级测试报告，只补测跨子 Session 交集缺口和整体启动冒烟，不重复任何子 Session 已覆盖的测试范围。
