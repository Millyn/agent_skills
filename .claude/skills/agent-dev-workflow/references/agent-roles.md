# Agent 角色与职责

> 本文是以下内容的唯一权威来源：四类角色职责、GUI 展示标识、任务边界格式、完成与测试报告格式、验收流程。
> Thread 与 Agent 的概念区别和 `create_thread` 使用规则见 [thread-management.md](thread-management.md)；AGENTS.md 中保存了任务边界格式的速查副本。

## 层级与角色总览

| 层级 | 角色 | 核心职责 |
|------|------|----------|
| 主 Thread | 流程统筹 Agent | 需求拆解、`create_thread`（失败时按降级链处理）创建子 Thread、跨子 Thread 交集测试、整体冒烟、最终验收和交付 |
| 子 Thread | 子 Thread 主 Agent | 任务规划、拆解、下发给子 Agent、判断测试启动时机、处理多子 Agent 重叠 |
| 子 Thread 内 | 任务执行 Agent（子 Agent） | 执行具体技术任务 + 单元测试自测 |
| 子 Thread 内 | 质量验证 Agent（测试 Agent） | 唯一的正式交互/功能测试层，所有编写性工作完成后统一启动 |

## GUI 展示标识规范

- 四类角色的展示名称固定为："流程统筹 Agent""子 Thread 主 Agent""任务执行 Agent""质量验证 Agent"，不得仅显示"主 Agent""子 Agent""测试 Agent"
- 展示名称必须与当前任务状态同时显示：`<角色展示名称>｜<任务状态>`，例如：`任务执行 Agent｜工作中`
- 子 Thread 级别需带 Thread 标识：`Thread:<Thread名称>｜<角色展示名称>｜<任务状态>`，例如：`Thread:thread-翻译功能｜任务执行 Agent｜工作中`
- Thread 名称使用注册表中的稳定名称（见 [thread-management.md](thread-management.md)）

## 流程统筹 Agent（主 Thread）

整个开发任务的负责人，对最终结果负责。

### 核心职责

- 理解用户需求、分析项目、调研 GitHub 开源项目（流程见 [development-workflow.md](development-workflow.md)）
- 按 UPDATE.MD 确定版本目标（见 [version-management.md](version-management.md)）
- 拆解需求，按 `create_thread` 规则创建子 Thread（见 [thread-management.md](thread-management.md)），同领域优先复用已有专项 Thread
- 为每个子 Thread 定义任务边界（使用下文「主 Thread 任务拆解格式」）
- 创建 `.m-work-flow` 目录并向子 Thread 提供上下文（目录规范见 [development-workflow.md](development-workflow.md)）
- 为每个子 Thread 提供完成时间预估，定期抽查子 Thread 状态并执行超时问询（机制见 [development-workflow.md](development-workflow.md)）
- 发现子 Thread 跑偏、卡顿、缺少权限或执行条件不足时及时介入纠正；必要时授予权限或代为处理
- 验收子 Thread 结果（见下文「验收流程」），处理跨子 Thread 冲突，最终合并所有修改
- 只测跨子 Thread 交集和整体启动冒烟，复用子 Thread 测试结论（见 [testing.md](testing.md)）
- 更新 Changelog、README，执行或提醒 Git 操作，最终向用户交付（见 [delivery.md](delivery.md)）

### 抽查重点

- 子 Thread 工作是否围绕分配的任务
- 是否长时间无进展、卡顿或重复尝试
- 是否发生越权修改、需求扩张或未经授权的架构调整
- 是否遇到权限、依赖、环境等阻塞问题

## 子 Thread 主 Agent

子 Thread 内部的规划者，负责将子 Thread 任务进一步拆解并下发给子 Agent，对主 Thread 汇报。

### 核心职责

- 接收主 Thread 分配的任务，分析任务细节和依赖关系
- 将任务拆解为最小可执行单元，为每个子 Agent 定义任务边界（使用下文「子 Thread 任务定义格式」）
- 为子 Agent 提供时间预估和检查点，监督进度并执行超时问询（机制见 [development-workflow.md](development-workflow.md)）
- **汇总自测结果并汇报主 Thread**：确认所有子 Agent 编码和自测完成后，直接汇总自测结果汇报给主 Thread，无需重复检查单元测试结果
- **处理多子 Agent 重叠覆盖**：识别子 Agent 之间的重叠区域，通知主 Thread 由主 Thread 创建独立测试 Agent 负责重叠区域的集成测试（协调规则见 [testing.md](testing.md) 多子 Agent 测试协调）
- 验收子 Agent 完成结果（见下文「验收流程」），向主 Thread 汇报整体完成情况

## 任务执行 Agent（子 Agent）

针对特定工作单元的执行者。**完成任务，而不是重新定义任务。**

### 必须遵守

- 只处理子 Thread 主 Agent 分配的任务，避免分析与当前任务无关的大量代码
- 不主动扩展需求，不自行增加用户没有要求的功能，不自行改变整体架构
- 不修改其他 Agent 明确负责的范围
- 发现任务与已有代码冲突时，向子 Thread 主 Agent 汇报

### 修改边界与"变更预算"

不因"可以顺便优化"而主动修改代码，除非满足以下条件之一：

- 该修改属于当前任务的必要依赖
- 子 Thread 主 Agent 明确授权
- 不修改会导致当前任务无法完成

否则应向子 Thread 主 Agent 汇报，而不是自行修改。发现可以重构、优化、增加新功能但不属于当前需求时：**默认不处理，记录并向子 Thread 主 Agent 汇报。**

### 自测要求

完成后只做单元测试层的自测：编译通过、启动不报错、所改功能点的单元测试和基本输入输出验证。不覆盖影响链路、不验证前端交互、不做 API 边界测试。完整的交互/功能验证由质量验证 Agent 统一负责（测试生命周期见 [testing.md](testing.md)）。

---

## 质量验证 Agent（测试 Agent）

唯一的正式交互/功能测试层。在所有子 Agent 编码和自测完成后统一启动（触发条件见 [testing.md](testing.md) 测试触发条件）。测试范围由子 Thread 主 Agent 在任务边界中确定（修改范围、影响范围、测试目标、测试边界）；除非用户明确要求，不默认执行全量测试，也不重复子 Agent 已通过的单元测试。测试策略、范围决策和全量回归触发条件见 [testing.md](testing.md)。其测试报告是子 Thread 验收、主 Thread 验收和最终交付汇总的唯一测试证据来源。

## 任务边界格式（权威模板）

### 主 Thread 任务拆解格式

主 Thread 创建子 Thread 时必须定义：

```
子 Thread：<名称>
任务：<描述>
负责：<范围>
依赖：<其他子 Thread>
修改范围：<实际允许变更的模块、文件或功能>
影响范围：<直接调用链、依赖模块、资源、数据或用户流程>
测试目标：<需要验证的行为和风险>
测试边界：<本次默认不覆盖的范围；如需全量回归需明确说明>
验收标准：<标准列表>
```

### 子 Thread 任务定义格式

子 Thread 主 Agent 分配子 Agent 任务时必须定义：

```
任务：<描述>
负责：<范围>
允许修改：<文件列表>
禁止修改：<文件列表>
依赖：<依赖项>
修改范围：<实际允许变更的模块、文件或功能>
影响范围：<直接调用链、依赖模块、资源、数据或用户流程>
测试目标：<需要验证的行为和风险>
测试边界：<本次默认不覆盖的范围；如需全量回归需明确说明>
验收标准：<标准列表>
```

子 Thread 主 Agent 分配任务时必须填写四项测试相关信息；质量验证 Agent 依据这些信息制定测试（详见 [testing.md](testing.md) 测试范围决策）。

### 示例

```
任务：实现用户登录 API
负责：后端登录接口

允许修改：
- src/api/auth/*
- src/services/auth/*
- tests/auth/*

禁止修改：
- src/frontend/*
- database/*
- package.json

验收标准：
- 登录接口能够正常运行
- 正确账号密码能够登录
- 错误账号密码能够正常返回错误
- 不影响现有 API
```

## 完成与测试报告格式（权威模板）

报告必须真实反映实际修改，不得隐瞒修改、声称已测试但实际没有、声称完成但实际没有、忽略任务范围之外的修改。

### 任务执行 Agent 完成报告

```
任务：<子 Thread 主 Agent 分配的任务>

修改文件：
- <file 1>

完成内容：
- <完成内容 1>

自测结果：
- 编译：<通过/失败>
- 单元测试：<通过/失败，覆盖率>
- 所改功能点验证：<验证方式与结果>
- 自测结论：<通过/有已知问题（说明）>

发现的问题：
- <问题或"无">

额外修改：
- <是否存在任务范围之外的修改，无则填"无">

需要子 Thread 主 Agent 注意：
- <需要关注的内容，无则填"无">
```

### 质量验证 Agent 测试报告

```
测试对象：<修改范围和影响范围>

测试结果：
- <通过/失败及详情>

实际测试范围：
- <已执行的修改范围、直接影响链路和必要的最小冒烟验证>

未测试范围及原因：
- <按测试边界列出；无则填写"无">

范围扩大及理由：
- <超出分配测试边界时必填；无则填写"无">

前后端一致性验证：
- <涉及前后端交互时必填：API 请求验证、前端渲染验证、状态同步验证>
- 不涉及前后端交互时填写"不涉及"

发现的问题：
- <问题或"无">
```

### 子 Thread 完成报告

```
子 Thread：<名称>

完成任务：
- <任务 1>

包含子 Agent：
- <子 Agent 1>

测试情况：
- <质量验证 Agent 测试结论及来源；未单独分配质量验证 Agent 时记录简化决定和理由>

汇总结果：
- <整体完成情况>

需要主 Thread 注意：
- <需要关注的内容，无则填"无">
```

## 验收流程

### 子 Thread 主 Agent 验收子 Agent

检查清单：

1. 是否完成原始任务
2. 是否修改了正确的文件
3. 是否修改了不应该修改的文件
4. 是否引入额外功能
5. 是否产生与项目现有逻辑冲突的修改
6. 是否存在没有事实依据的设计
7. 是否符合任务边界
8. 自测结果是否可信（单元测试是否通过）
9. 是否影响其他子 Agent 的工作

验收方式为审查证据：核对报告、修改文件和测试结论，不重新执行已被覆盖的测试；仅在发现覆盖缺口时补测缺口。

#### 验收不通过处理

发现跑偏时：**立即停止其继续扩展，并纠正任务范围。不要让错误方向继续积累代码。**

发现其他验收问题（BUG、功能不达标、测试不通过、范围越界）时：

```
验收发现问题
    │
    ▼
退回给对应子 Agent 修复
    │  修复要求：明确指出问题、限定修复范围、要求修复后自测
    │
    ▼
子 Agent 修复 + 单元测试自测
    │
    ▼
子 Thread 主 Agent 再次验收
    │
    ├── 通过 → 汇总自测结果汇报主 Thread
    └── 不通过 → 再次退回（累计第 2 轮）
    │
    ▼
第 3 轮仍不通过 → 升级：通知主 Thread，由主 Thread 创建新的独立 Thread 负责修复
```

**升级条件**：同一子 Agent 同一任务累计 3 轮验收不通过时，必须升级处理。新 Thread 拥有独立的修改范围和任务边界，原子 Agent 的上下文作为参考提供给新 Thread。

### 子 Thread 主 Agent 汇报主 Thread

所有子 Agent 验收完成后，子 Thread 主 Agent 直接汇总自测结果汇报给主 Thread：

- 检查所有子 Agent 完成报告和自测结果
- 确认子 Agent 之间无未解决的冲突
- 确认依赖关系已满足
- 直接汇总自测结果汇报给主 Thread，无需重复检查单元测试结果
- 主 Thread 根据修改范围和风险判断是否需要启动质量验证 Agent

#### 质量验证发现问题处理

质量验证 Agent 测试报告中"发现的问题"不为空时：

```
质量验证发现问题
    │
    ▼
主 Thread 评估问题
    │
    ├── 问题属于某个子 Thread 的修改范围 → 退回给该子 Thread 修复
    │       修复后重新自测 → 子 Thread 主 Agent 汇报主 Thread → 质量验证 Agent 补测
    │
    ├── 问题属于多子 Thread 交集或集成问题 → 创建独立测试 Agent + 修复子 Thread
    │       修复后质量验证 Agent 补测
    │
    └── 问题属于任务边界设计缺陷 → 主 Thread 决策调整边界
```

质量验证 Agent 只负责测试和报告，不负责修复。修复由子 Agent 执行，修复后的验证由质量验证 Agent 补测完成。

### 主 Thread 验收子 Thread

检查清单：

1. 子 Thread 是否完成分配的所有任务
2. 子 Thread 内部是否有未解决的冲突
3. 子 Thread 的修改是否影响其他子 Thread
4. 整体结果是否符合用户需求
5. 是否存在超出需求范围的功能
6. 测试结果是否可信

验收方式为审查证据：汇总各级测试报告，执行跨子 Thread 交集测试和整体冒烟测试（冒烟标准见 [testing.md](testing.md) 冒烟测试），不重复任何子 Thread 已覆盖的测试范围。

#### 验收不通过处理

```
主 Thread 验收发现问题
    │
    ▼
打回给对应子 Thread 修复
    │  修复要求：明确指出问题、限定修复范围
    │
    ▼
子 Thread 内部执行修复（子 Agent 修复 → 自测 → 汇报主 Thread）
    │
    ▼
主 Thread 再次验收
    │
    ├── 通过 → 进入合并与交付
    └── 不通过 → 再次打回（累计第 2 轮）
    │
    ▼
第 3 轮仍不通过 → 升级：创建新的独立 Thread 负责整体修复
```

**升级条件**：同一子 Thread 累计 3 轮验收不通过时，必须升级处理。新 Thread 拥有独立的修改范围和任务边界，原子 Thread 的全部上下文作为参考提供给新 Thread。主 Thread 向用户汇报情况并提供修复计划。
