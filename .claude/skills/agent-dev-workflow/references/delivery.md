# 交付规范

## 多层级交付架构

### 交付流程

```
子 Agent 完成 → 子 Thread 主 Agent 验收 → 主 Thread 验收 → 最终交付用户
```

### 各层级职责

#### 子 Agent
- 完成分配的任务
- 提交完成报告给子 Thread 主 Agent

#### 子 Thread 主 Agent
- 验收子 Agent 的完成结果
- 汇总子 Thread 内部的修改
- 提交子 Thread 完成报告给主 Thread

#### 主 Thread（流程统筹 Agent）
- 验收所有子 Thread 的完成结果
- 合并所有修改
- 只测跨子 Thread 交集和整体启动冒烟，复用子 Thread 测试结论
- 更新文档
- 交付用户

## 主 Thread 合并规范

所有子 Thread 工作完成之后，由主 Thread（流程统筹 Agent）负责最终合并。

### 合并前检查

1. 检查所有子 Thread 的修改
2. 检查子 Thread 之间是否存在冲突
3. 检查是否产生重复实现
4. 检查是否存在超出需求范围的代码
5. 检查整体项目结构
6. 复核各级测试报告是否齐全可信，只补测跨子 Thread 交集缺口和整体启动冒烟
7. 确认最终结果符合用户需求

**主 Thread 不应直接机械拼接所有子 Thread 的代码。最终代码必须作为一个完整项目进行判断。**

## Changelog 版本管理

完成正式开发任务并合并修改后，应主动更新项目的 Changelog。

### Changelog 至少记录

- 当前版本
- 新增功能
- 修改内容
- 修复问题
- 重要行为变化

如果项目已存在 Changelog，应遵循项目现有格式。如果没有，根据项目规模和用户需求判断是否需要新增。

## Git 操作规范

### 用户已提出明确 Git 要求

- 按用户要求执行 Git 操作
- 按用户指定的分支、提交方式和提交信息规则执行
- 不自行改变用户明确要求的 Git 工作流

### 用户未提出 Git 要求

主 Thread（流程统筹 Agent）在完成开发后应提醒用户：
- 当前修改是否已经完成
- 是否需要执行 Git commit
- 是否需要创建 tag
- 是否需要推送远程仓库

**不要因为用户没有明确要求就擅自改变用户的 Git 工作流。**

## README 文档

项目交付时，主 Thread 必须检查 README。

### README 应至少包含

#### 项目使用的库

说明项目运行或构建需要的：
- 主要依赖
- 第三方库
- 框架
- 运行环境

#### 编译命令

必须提供用户可以直接使用的编译/构建命令。

```bash
npm install
npm run build
```

具体命令必须根据项目实际技术栈填写。**不允许凭空编造编译命令。**

#### 使用说明

尽可能提供：
- 安装方法
- 配置方法
- 启动方法
- 编译方法
- 运行方法

**目标：即使用户未来只进行少量代码修改，也能够根据 README 自行完成编译。**

## 最终交付检查清单

在最终向用户交付之前，主 Thread 应确认：

- [ ] 需求已经实现
- [ ] 子 Thread 的修改已经全部验收
- [ ] 没有明显超出需求范围的功能
- [ ] 各级测试报告齐全，跨子 Thread 交集和启动冒烟已验证
- [ ] Changelog 已更新
- [ ] UPDATE.MD 已根据版本开发结果更新
- [ ] Thread 注册表已更新（各子 Thread 状态置为"待复用"）
- [ ] README 已更新
- [ ] 依赖和编译方法已经说明
- [ ] Git 操作要求已经处理或提醒用户
- [ ] 已知问题已经向用户说明
- [ ] 环境权限已正确设置（开发环境权限全面打开，正式环境需用户确认）
- [ ] 数据库清理已完成（如部署到线上开发环境）

## 最终向用户说明

1. 完成了什么
2. 修改了哪些主要模块
3. 测试了什么
4. 哪些内容没有测试
5. 是否存在已知限制
6. Git 当前状态
7. 用户下一步需要执行什么操作
8. 当前环境类型（开发环境/线上开发环境/正式环境）及权限设置
9. 数据库清理和初始化状态（如适用）

## 语言规范

### 默认用户端语言

当用户未明确指定用户端语言时，默认设置为**中文**。

### 适用范围

该语言规则主要适用于用户可直接看到的展示层内容：
- Web / App / Desktop UI 文案
- 菜单、按钮、提示、错误信息、状态文本
- 用户可见的配置说明
- 用户可见的帮助信息和引导内容

### 不适用范围

以下内容可继续使用项目原有语言或英文：
- 代码、变量名、函数名
- 日志字段、调试信息
- 其他明确属于开发者内部使用的技术内容

### 用户指定语言

如果用户明确指定其他用户端语言，则以用户指定语言为最高优先级，不得擅自改回中文。

## 环境权限规范

### 环境类型判定

在用户未明确说明当前环境是正式环境时，一律视为**开发环境或线上开发环境**。

### 权限策略

- **开发环境/线上开发环境**：权限全面打开，无需反复过问用户是否授权
- **数据重要性和安全性**：在开发环境中完全忽略，直至用户提出要求时才需考虑
- **正式环境**：仅在用户明确说明时适用正式环境权限策略

### 执行要求

1. Agent 在执行部署、数据库操作、配置修改等操作前，无需询问用户是否授权（除非用户明确说明是正式环境）
2. 开发环境中的操作应以效率优先，避免因权限确认流程影响开发进度
3. 当用户后续提出数据重要性或安全性要求时，应立即调整相应策略
4. 开发环境中必要的密钥、密码、邀请码、数值等校验数据，应记录在 `.m-work-flow/password.md` 中，便于测试使用

## 数据库清理规范

### 默认清理策略

在用户无特殊说明的情况下，每次部署到线上开发环境时应**自动清理历史数据库**。

### 清理流程

```
部署到线上开发环境
    │
    ▼
自动清理历史数据库
    │  目的：保证数据库无脏数据污染
    │
    ▼
检查数据库是否需要初始化数据
    │
    ├── 需要初始化 → 执行数据初始化
    └── 无需初始化 → 清理完成
```

### 执行要求

1. **自动清理**：部署到线上开发环境时自动执行数据库清理，无需用户额外指令
2. **数据初始化**：清理完成后，如果数据库存在需初始化的数据，则再次初始化
3. **环境区分**：正式环境不自动清理，需用户明确指令
4. **清理范围**：清理历史数据、测试数据、临时数据，保留必要的系统配置和结构
5. **初始化内容**：根据项目需求初始化必要的基础数据、配置数据、示例数据等
