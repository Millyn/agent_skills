# 测试规范

## 测试生命周期

子 Thread 内的测试遵循简化的阶段顺序，每个阶段有明确的执行者和触发条件：

```
子 Agent 编码完成
    │
    ▼
阶段 1：子 Agent 自测（单元测试）
    │  执行者：任务执行 Agent
    │  内容：编译、启动、单元测试、所改功能点基本行为验证
    │  产出：自测结果（记录在完成报告中）
    │
    ▼
所有子 Agent 编码 + 自测完成
    │
    ▼
阶段 2：子 Thread 主 Agent 汇报主 Thread
    │  动作：直接将子 Agent 自测结果汇总后汇报给主 Thread
    │  无需：重复检查单元测试结果
    │
    ▼
阶段 3：主 Thread 安排后续测试流程
    │  执行者：主 Thread（流程统筹 Agent）
    │  内容：根据修改范围和风险判断是否启动质量验证、冒烟测试等
    │  产出：测试计划和执行安排
    │
    ▼
阶段 4：质量验证 Agent 执行（交互/功能测试）（如需要）
    │  执行者：质量验证 Agent
    │  触发条件：主 Thread 判断需要交互/功能验证
    │  内容：交互性测试、API 边界、前端输入边界、前后端衔接
    │  产出：标准测试报告
    │
    ▼
阶段 5：主 Thread 验收（跨 Thread 交集 + 冒烟测试）
```

### 关键规则

1. **子 Agent 自测完成后直接汇报主 Thread**：子 Thread 主 Agent 无需重复检查单元测试结果，直接汇总子 Agent 自测结果后汇报给主 Thread。
2. **主 Thread 统一安排后续测试**：由主 Thread 根据修改范围、风险和项目需求判断是否启动质量验证、冒烟测试等。
3. **质量验证 Agent 每个子 Thread 只跑一次**，覆盖该子 Thread 所有子 Agent 的修改范围（如需要）。
4. **子 Agent 自测和质量验证 Agent 测试不重叠**：自测 = 单元测试，质量验证 = 交互/功能测试。

## 测试触发条件

### 质量验证 Agent 启动条件

主 Thread（流程统筹 Agent）判断以下条件全部满足后，启动质量验证 Agent：

- 所有子 Thread 已汇报完成
- 所有子 Agent 自测结果为通过（或已记录已知问题）
- 子 Thread 之间的依赖关系已满足（前置子 Thread 的输出已就绪）
- 没有未解决的阻塞或冲突
- 修改范围需要交互/功能验证

### 可跳过质量验证 Agent 的条件

主 Thread 可决定不单独分配质量验证 Agent，但必须同时满足：

- 修改范围很小且风险低
- 不涉及前后端交互、API 变更、数据流变更
- 不涉及用户可感知的界面或交互行为
- 主 Thread 在验收记录中记录该决定和理由

## 自测与质量验证的职责边界

### 子 Agent 自测（单元测试层）

**定位**：确认代码层面的正确性，不是功能验证。

| 必须做 | 不做 |
|--------|------|
| 编译通过 | 影响链路测试 |
| 启动不报错 | 前端交互验证 |
| 所改功能点的单元测试 | API 边界测试 |
| 所改功能点基本输入输出验证 | 跨模块集成测试 |
| 语法错误、类型错误检查 | 用户流程验证 |

**自测报告格式**（记录在任务执行 Agent 完成报告中）：

```
自测方式：
- 编译：<通过/失败>
- 单元测试：<通过/失败，覆盖率>
- 所改功能点验证：<验证方式与结果>

自测结论：<通过/有已知问题（说明）>
```

### 质量验证 Agent 测试（交互/功能测试层）

**定位**：确认功能层面的正确性和用户体验，是唯一的正式定向测试。

| 必须做 | 不做 |
|--------|------|
| 交互性测试（前端页面操作、表单提交、按钮点击等） | 重复子 Agent 已通过的单元测试 |
| API 边界测试（参数校验、异常返回、鉴权） | 与修改无关的功能测试 |
| 前端输入框边界（空值、超长、特殊字符、注入） | 性能测试（除非用户要求） |
| 前后端衔接验证（请求参数、响应处理、状态同步） | 代码审查 |
| 状态流转测试（业务流程的完整路径） | |
| 错误场景测试（网络异常、权限不足、数据不存在） | |

**前端项目的特殊要求**：

- 必须调用 MCP 浏览器能力（或等效工具）模拟用户操作前端界面
- 必须验证前端发起的 API 请求参数、请求头、请求时机是否正确
- 必须验证后端 API 返回后前端的渲染和状态更新是否正确
- 必须测试前端输入框的各种边界条件

**质量验证 Agent 测试报告格式**：

```
测试对象：<修改范围和影响范围>

测试结果：
- <通过/失败及详情>

实际测试范围：
- <已执行的修改范围、直接影响链路和必要的最小冒烟验证>

未测试范围及原因：
- <按测试边界列出；无则填写"无">

范围扩大及理由：
- <超出分配测试边界时必填；无则填写"无">

发现的问题：
- <问题或"无">

前后端一致性验证：
- <涉及前后端交互时必填：API 请求验证、前端渲染验证、状态同步验证>
- 不涉及前后端交互时填写"不涉及"
```

## 多子 Agent 测试协调

### 场景 1：子 Agent 之间无重叠

各子 Agent 修改不同模块、无文件和逻辑交叉：

- 每个子 Agent 完成自测
- 全部完成后，质量验证 Agent 统一测试各子 Agent 的修改范围
- 无需额外协调

### 场景 2：子 Agent 之间有重叠覆盖

多个子 Agent 修改了相同模块或存在调用关系：

- 子 Thread 主 Agent 必须识别重叠区域
- 通知主 Thread，由主 Thread 创建新的独立测试 Agent 负责重叠区域的集成测试
- 新测试 Agent 的测试范围 = 重叠区域的端到端流程
- 该测试独立于各子 Agent 的自测和质量验证 Agent 的定向测试

### 场景 3：子 Agent 之间有依赖

子 Agent B 依赖子 Agent A 的输出（如 A 改了 API，B 改了调用方）：

- 子 Agent B 必须等子 Agent A 完成后才能开始自测
- 质量验证 Agent 测试时，必须验证 A→B 的完整链路
- 子 Thread 主 Agent 在分配任务时必须标注依赖关系

## 前后端一致性测试原则

**核心原则：修改了后端业务逻辑时，必须同步验证前端是否按预期调用和展示；修改了前端交互时，必须同步验证后端接口是否正确响应。**

### 适用场景

- 后端修改了 API 接口（参数、返回值、错误码、鉴权逻辑）→ 前端必须测试对应的调用和展示
- 后端修改了业务规则（数据校验、状态流转、权限控制）→ 前端必须测试相关流程是否正常
- 前端修改了请求方式或数据处理逻辑 → 后端必须测试接口兼容性
- 前后端同时修改 → 必须联合验证端到端流程

### 执行要求

1. **任务边界中必须标注端到端影响**：子 Thread 主 Agent 分配任务时，若修改涉及前后端交互，必须在影响范围中明确标注受影响的前端/后端组件，质量验证 Agent 据此制定跨端测试。
2. **测试报告必须记录跨端验证结论**：质量验证 Agent 测试报告中，若修改涉及前后端交互，必须单独列出前后端一致性验证结果，不能只测一端。
3. **禁止只测后端不验前端**：后端接口行为变更后，不能仅凭接口测试通过就判定完成，必须确认前端调用方（页面、组件、脚本）能正确使用新行为。
4. **禁止只测前端不验后端**：前端展示逻辑变更后，不能仅凭页面渲染通过就判定完成，必须确认后端实际返回的数据和行为与前端预期一致。

### 与测试唯一责任制的衔接

前后端一致性测试属于质量验证 Agent 的定向测试范围，不因前后端分属不同模块而拆分到多个层级重复执行。质量验证 Agent 应在一次定向测试中同时覆盖后端逻辑和前端调用/展示，避免前后端各自测试但无人验证衔接点。

## 测试唯一责任制

**核心原则：同一修改范围的完整测试只在一个层级执行一次，其余层级审查证据并复用结论，不重新执行相同测试。**

目的：消除多层级重复测试造成的 Token、时间和计算资源浪费。

### 各层级测试职责

| 层级 | 角色 | 测试职责 | 明确禁止 |
|------|------|----------|----------|
| 执行层 | 任务执行 Agent | 单元测试：编译、启动、单元测试、所改功能点基本行为验证 | 不覆盖影响链路；不产出正式测试报告 |
| 验证层 | 质量验证 Agent | 交互/功能测试：API 边界、前端交互、前后端衔接、状态流转、错误场景 | 不重复执行子 Agent 已通过的单元测试 |
| 主 Thread 验收层 | 流程统筹 Agent | 跨子 Thread 交集测试 + 整体冒烟测试 + 验收审查 | 不重复任何子 Thread 已覆盖的测试范围 |

### 复用规则

- 下游层级直接引用上游测试结论作为证据，引用时必须标注来源（执行角色、所在报告、覆盖范围）。
- 禁止对同一修改范围重复执行相同的测试命令或等效测试。
- 子 Thread 主 Agent 无需重复检查子 Agent 已通过的单元测试结果，直接汇总汇报给主 Thread。
- 主 Thread 统一安排后续测试流程，根据需要决定是否启动质量验证、冒烟测试等。
- 上游证据缺失、不可信或存在覆盖缺口时，下游可以要求补测或自行补测，并在报告中记录缺口和补测理由。
- 最终交付说明中的"测试了什么 / 未测试什么"直接汇总各级报告结论，交付前不重新测试。

### 小型任务简化

当子 Thread 的修改范围很小且风险低时，主 Thread 可决定不单独分配质量验证 Agent，以任务执行 Agent 自测加主 Thread 定向抽查代替，但必须在验收记录中记录该决定和理由。

## 验收问题处理闭环

验收（包括质量验证、子 Thread 验收、主 Thread 验收）发现问题后，必须走明确的修复-再验收闭环，而不是停留在"发现问题"。

### 质量验证发现问题

质量验证 Agent 测试报告中"发现的问题"不为空时，子 Thread 主 Agent 按以下流程处理：

```
质量验证发现问题
    │
    ▼
子 Thread 主 Agent 评估问题归属
    │
    ├── 问题属于某个子 Agent 的修改范围
    │       → 退回给该子 Agent 修复（限定修复范围 + 要求自测）
    │       → 修复后子 Agent 自测 → 子 Thread 主 Agent 验收
    │       → 质量验证 Agent 补测（仅验证修复点和影响范围）
    │
    ├── 问题属于多子 Agent 交集或集成问题
    │       → 子 Thread 主 Agent 创建独立测试 Agent 定位问题
    │       → 分配给相关子 Agent 修复 → 修复后统一补测
    │
    └── 问题属于任务边界设计缺陷
            → 汇报主 Thread，由主 Thread 决策是否调整边界
```

**质量验证 Agent 只负责测试和报告，不负责修复。** 修复由子 Agent 执行，修复后的验证由质量验证 Agent 补测完成。

### 子 Thread 主 Agent 验收发现问题

退回给对应子 Agent 修复，修复后重新验收。累计 3 轮验收不通过时升级：通知主 Thread，由主 Thread 创建新的独立 Thread 负责修复（详见 [agent-roles.md](agent-roles.md) 验收流程）。

### 主 Thread 验收发现问题

打回给对应子 Thread 修复，修复后重新验收。累计 3 轮验收不通过时升级：创建新的独立 Thread 负责整体修复，向用户汇报情况（详见 [agent-roles.md](agent-roles.md) 验收流程）。

### 修复-再验收的测试要求

1. 子 Agent 修复后必须重新自测（单元测试），自测通过后才能提交验收。
2. 质量验证 Agent 的补测只验证修复点和直接影响范围，不重跑全量定向测试。
3. 补测报告中必须标注"补测"，与首次测试报告区分，并引用首次报告作为基线。
4. 升级为新 Thread 时，新 Thread 拥有独立的任务边界，沿用原 Thread 的测试结论作为参考，但必须重新执行验收流程。
5. 子 Agent 修复后的自测结果直接汇报给主 Thread，主 Thread 统一安排后续验证流程。

## 测试范围决策

### 分配前的影响分析

主 Thread 在安排测试时，必须明确：

- **修改范围**：实际允许变更的模块、文件或功能。
- **影响范围**：修改直接影响的调用链、依赖模块、资源、数据或用户流程；无法确认的部分应标明待验证风险。
- **测试目标**：需要验证的行为、验收标准和主要风险。
- **测试边界**：本次默认不覆盖的模块、流程或非直接相关功能。

质量验证 Agent 必须依据上述信息制定测试，并在发现实际影响超出分配范围时先记录风险，必要时向主 Thread 汇报后扩大测试范围。

### 默认测试策略

用户未明确要求全量回归时，主 Thread 默认执行定向测试，范围按以下优先级确定：

1. 修改范围内的单元、模块或功能测试。
2. 修改直接影响的调用链、依赖模块、资源、数据和关键用户流程。
3. 为确认程序可启动、主流程未被破坏而进行的必要的最小冒烟验证。

不得仅因为项目规模、测试命令默认行为或"全面测试"的惯例，一味执行全项目测试。与本次修改没有直接关联的功能不属于默认测试范围。任何超出分配测试边界的测试，都必须在报告中记录实际扩大范围和扩大理由。

### 全量回归触发条件

以下情况必须全量回归，或在无法执行时由主 Thread 明确记录风险并说明替代验证方案：

- 用户明确要求全量回归或完整项目测试。
- 修改涉及全局配置、构建流程、依赖版本、公共基础设施、通用组件或跨模块契约，影响范围难以限定。
- 修改涉及数据格式、数据库结构、迁移、公共接口或核心状态管理，可能影响多个未直接修改的功能。
- 修改范围或影响范围无法可靠识别，且定向测试不足以证明系统整体可用。

以下情况建议全量回归，由主 Thread 根据风险、成本和项目约束决定，并记录决定理由：

- 修改跨越多个业务域或多个端（例如前端、后端、任务执行链路）。
- 修改核心启动流程、认证授权、路由、资源加载或错误处理等公共链路。
- 定向测试发现回归问题，或变更触及大量既有测试。
- 发布前、版本验收或用户明确关注整体稳定性。

除用户明确要求外，选择全量回归不是默认义务；选择定向测试也必须说明依据的修改范围和影响范围。

## 冒烟测试

冒烟测试用于验证系统整体可用，分两个层级：

### 子 Thread 级冒烟

主 Thread 在子 Thread 完成后执行，验证该子 Thread 的修改未破坏基本功能：

- 程序能够正常启动
- 主流程能够走通（不崩溃、不卡死）
- 该子 Thread 修改的核心功能基本可用

### 主 Thread 级冒烟（整体冒烟）

主 Thread 验收时执行，验证所有子 Thread 合并后系统整体可用：

- 根据用户的需求和交互需求，完整跑通核心业务场景
- 多个子 Thread 的修改合并不产生冲突
- 端到端流程（从用户入口到最终输出）完整可用
- 不崩溃、不出现明显功能退化

冒烟测试不替代定向测试和功能验证，仅作为最低限度的系统可用性确认。

## 测试范围记录

### 测试策略选择

#### 小型项目

可以进行较完整的全项目测试。

重点确认：
- 程序是否能够正常启动
- 核心流程是否能够正常执行
- 是否发生程序崩溃
- 是否存在资源加载失败
- 是否存在资源路径错误
- 是否存在明显运行时错误
- 是否存在新增功能导致的流程异常

#### 大型项目

不需要默认对整个项目进行全面测试。遵循本规范"测试范围决策"确定定向测试或全量回归。

应优先测试：
- 本次修改涉及的模块
- 本次修改影响的调用链
- 与本次修改直接相关的功能
- 修改涉及的资源、数据、关键流程

**目的：减少不必要的 Token、运行时间和计算资源消耗。**

对于未修改、且与本次修改没有直接关联的大量功能，不需要为了"全面测试"而重复验证。最终可以要求用户自行执行完整项目测试。

### 报告中的范围记录

质量验证 Agent 的完成报告必须记录：

- **实际测试范围**：实际执行的修改范围、直接影响链路、相关资源或数据，以及必要的最小冒烟验证。
- **未测试范围及原因**：按测试边界列出未覆盖内容，并说明是因为与修改无直接关联、环境或依赖不可用、时间成本、风险评估，还是其他具体原因；没有未测试范围时填写"无"。
- **范围扩大及理由**：如实际测试超出分配的测试边界，必须列出新增范围和扩大理由。

报告不能只写"测试通过"或只列测试命令而省略覆盖范围。

该报告是主 Thread 验收和最终交付汇总的唯一测试证据来源；各级验收和交付说明直接引用本报告，不重新执行相同测试。

## 测试范围

默认情况下，测试 Agent 主要关注程序功能和运行稳定性。

### 程序运行

确认程序能够正常启动和运行。

### 流程完整性

确认修改后的流程不会发生明显中断或崩溃。

### 资源加载

确认：
- 图片能够正常加载
- 音频能够正常加载
- 配置文件能够正常加载
- 数据文件能够正常读取
- 依赖资源路径正确

### 错误检查

重点关注：
- Runtime Error
- 程序崩溃
- 空引用
- 文件不存在
- 资源不存在
- 配置错误
- 数据格式错误
- 接口调用错误
- 明显的流程异常

## 性能测试原则

除非用户明确要求，否则默认不进行专门的性能测试。

### 不默认进行的测试

- Benchmark
- 压力测试
- 大规模并发测试
- 长时间运行测试
- CPU/GPU 性能分析
- 内存性能分析
- 极限负载测试

### 需要性能测试的情况

- 用户明确要求性能优化
- 当前修改明显涉及性能
- 项目本身存在明确性能问题

**首要保证程序功能正确，而不是为了性能测试消耗额外 Token 和计算资源。**
