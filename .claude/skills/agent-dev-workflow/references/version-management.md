# 版本管理规范

## UPDATE.MD 核心原则

**UPDATE.MD 是版本开发计划的事实来源**

- 用户要求读取下版本计划 → 先读取 UPDATE.MD
- 用户要求生成 Planner → 先读取 UPDATE.MD，再拆解需求
- 用户要求开发下一版本 → 先读取 UPDATE.MD，确认版本目标
- 多个版本存在 → 默认只处理下一版本
- 用户要求多版本开发 → 先与用户确认

## UPDATE.MD 文件格式

### 文件首行

```markdown
# 当前版本 {version}
```

### 版本更新规划

```markdown
# {version} 版本更新目的

[feature] 新功能描述

[bug] Bug 修复描述

[opt] 优化描述
```

### 标签说明

- `[feature]`：新功能
- `[bug]`：用户发现的 Bug
- `[opt]`：对历史功能进行优化

## 版本判断流程

1. 读取文件首行 `# 当前版本 {version}`
2. 判断当前项目版本
3. 读取后续版本规划
4. 将当前版本之后的第一个版本视为**下一版本**
5. 根据下一版本的更新目的确定开发目标

**禁止跳过当前版本判断，直接根据其他版本内容自行选择目标。**

## 多版本规划处理

当 UPDATE.MD 包含多个版本规划时：

```
当前版本：1.2.0
默认开发：1.3.0
暂不开发：1.4.0、1.5.0
```

如用户要求多版本开发，必须先确认：

> 当前 UPDATE.MD 中包含多个版本规划，是否需要进行多版本开发，还是只处理下一版本？

## 版本 Planner 流程

1. 读取 UPDATE.MD
2. 判断当前版本，找到下一版本
3. 读取所有 [feature]、[bug]、[opt] 项目
4. 分析每项更新涉及的模块
5. 拆解为最小开发单元
6. 规划子 Agent 工作范围（任务、负责范围、允许/禁止修改范围、依赖、验收标准）

**Planner 必须以 UPDATE.MD 中的版本目标为依据，不得擅自增加不存在的功能。**

## [feature] 处理原则

重点分析：
- 新增功能涉及的模块、接口、数据、UI、资源
- 与现有功能的依赖关系

然后拆解为具体开发单元。

## [bug] 处理原则

优先分析：
1. Bug 现象和涉及流程
2. 当前代码实际行为
3. Bug 产生原因
4. 最小修改范围
5. 修复后需要验证的流程

**优先修复问题，不应借机进行无关的大规模重构。**

## [opt] 处理原则

- 首先理解当前历史功能的实现方式
- 确定优化范围
- 最小修改范围，明确边界
- 不影响无关功能
- 不擅自增加新功能

## 版本完成后更新 UPDATE.MD

### 更新当前版本号

```markdown
# 当前版本 {旧 version}
→
# 当前版本 {新 version}
```

### 保留历史版本记录

```markdown
# 1.3.0 版本更新目的

[feature] 增加用户头像上传功能

[bug] 修复登录后偶发无法进入首页的问题

[opt] 优化历史文件上传流程

完成时间：YYYY-MM-DD
```

历史版本应记录：
- 哪个版本完成了哪些内容
- 版本原始开发目的
- 完成时间

## UPDATE.MD 与 CHANGELOG 的区别

| 文件 | 用途 | 重点回答 |
|------|------|----------|
| UPDATE.MD | 记录开发计划和版本规划 | 接下来准备开发什么？过去版本计划开发什么？ |
| CHANGELOG | 记录已完成并交付的版本变更 | 这个版本实际完成了什么？ |

**不能因为已更新 CHANGELOG，就跳过 UPDATE.MD 的更新。两者都应维护。**
